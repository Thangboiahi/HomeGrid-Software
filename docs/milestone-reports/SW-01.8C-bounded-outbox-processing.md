# SW-01.8C — Bounded Outbox Processing and Worker Execution Controls

**Status:** Implemented and verified locally  
**Date:** 2026-11-09  
**Environment:** Local Auth/Firestore emulators, project `demo-homegrid` only  
**Production resources:** Not accessed; no deployment performed

## Existing behavior and approved implementation

Before this work, both account-access and session-sign-out processors traversed their complete operation collections in document-ID order, filtered eligibility in application code, and awaited each operation sequentially. Claims already enforced `nextAttemptAt`, `leaseExpiresAt`, and per-operation lease tokens. The account lease was five minutes; the session lease was one minute. Auth calls were performed outside Firestore transactions, with operation/audit state persisted through transactions.

This work replaces collection scans with separate indexed queries for due `pending` records and expired `processing` leases. It bounds candidate selection, claims, pages, concurrency and runtime independently; emits separate domain summaries; and renews active leases without changing the established lease durations. Existing lease-token checks continue to fence stale checkpoints and finalization. A local combined runner invokes both domain processors independently and reports each result.

## Processing design

- `firebase/firestore.indexes.json` defines the status plus due-time composite indexes for both outboxes.
- `selectDueOutboxCandidates` paginates each eligible status stream fairly and stops at candidate, page or deadline bounds.
- Default bounds are 100 candidates, 20 claims, 8 pages of up to 25, concurrency 2 and 45 seconds. The final two seconds are reserved from new claims. The `HOMEGRID_ACCOUNT_OUTBOX_*` and `HOMEGRID_SESSION_OUTBOX_*` environment settings override each bound for the corresponding local worker.
- During a claim, a server-side heartbeat renews the existing lease transactionally. It validates operation ID, processing status and lease token before extending expiration. Existing service transactions still validate the token before checkpoints, failure persistence and completion.
- Per-operation errors are counted without halting sibling operations. Candidate query errors produce a failed domain summary. The combined runner uses independent settled results so one domain failure does not suppress the other.
- Existing account suspension/reactivation and session sign-out retry, audit, and state-machine behavior remains in the domain coordinators. No shared state machine was introduced.
- The account lease remains five minutes; the session lease remains one minute.

## Worker execution controls

`npm run process:outboxes:demo` starts the combined worker under local Firebase emulators and rejects production projects or non-loopback Auth/Firestore endpoints. Individual local recovery commands remain available. Per-domain summary fields include selected candidates, pages, claim attempts, successful claims, status counts, operation errors, deadline status, duration and a sanitized infrastructure failure code. No user identifier, cookie, token or raw Auth response is included in the new runner summary.

## Verification

The focused integration suite selects only due pending and expired processing records, excludes future-due, active-lease and completed records, and verifies candidate/page/deadline bounds. Unit tests cover configured budgets, worker concurrency, operation-level error isolation, and domain isolation. The existing session-sign-out integration suite additionally verifies lease renewal while an Auth call is deliberately held and confirms a second processor cannot claim the renewed lease.

## Limitations and operational gates

- Firebase cannot cancel an already-issued query or Auth request when the local deadline expires; the worker checks the deadline before queries, between pages, and before claims. A currently running operation is protected by its renewed lease and token fence.
- Query latency, Auth API latency and worker runtime still require production monitoring and alert thresholds before scheduling.
- IAM contents, production project mapping, scheduler cadence, retry ownership and approved manual-recovery procedures remain deployment gates from SW-01.8B.
- No changes were made to role permissions, Firestore rules, account/session domain state machines, device features, or production deployment configuration.

## Acceptance recommendation
