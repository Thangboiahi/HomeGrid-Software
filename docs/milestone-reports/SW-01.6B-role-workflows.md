### Environment and native confirmation handling

The app, Auth Emulator, and Firestore Emulator were run locally with `demo-homegrid` and matching loopback endpoints. Three disposable role accounts and their fixtures were created in emulator storage. The browser was kept on `http://localhost:3000`, matching `APP_ORIGIN`.

The previous timeout was caused by awaiting the Playwright click before responding to the synchronous `window.confirm`. That leaves the page paused on the native dialog while the click action waits. The reliable sequence is to start the click promise, poll `tab.getJsDialog()`, accept or dismiss the returned `confirm`, and then await the click. Both acceptance and dismissal completed successfully with this sequence. Escape also dismissed the active native dialog; focus returned to the triggering “Save associations” button and the cancelled operation made no request or mutation. The dialog is browser-managed rather than an application DOM modal, so its exact browser-chrome bounds are not available to page-level geometry checks.

An initial login attempt used `127.0.0.1` while `APP_ORIGIN` was `localhost`; the server correctly rejected the origin. Retrying on the configured `localhost` origin established the test session. This was a local test URL mismatch, not an application authorization defect.

### Super Admin registry workflows

- **Search:** searching for the exact record ID displayed its one matching record. A non-matching query displayed “No records match this search.”
- **Registration:** created a physical-classified software registry record; it appeared in the registry as unassigned with the record-ID disclaimer.
- **Associations:** saving a matching Household A and Installation A succeeded; the record refreshed as assigned with both IDs displayed.
- **Invalid household:** an unknown household ID displayed “Household not found.” The record remained unassigned and no successful association audit event appeared.
- **Conflicting association:** an existing Household B paired with Installation A was rejected with “Invalid request.” The persisted Household A/Installation A values remained unchanged.
- **Product reassignment:** changed the record from Product A to Product B; the card refreshed to show Product B and its reference.
- **Invalid product reference:** while the product selector still held its previously loaded option, the Product B document was temporarily removed from the local emulator. Submitting that stale ID displayed “Invalid request.” and left the device’s product reference unchanged. Product B was restored to active state immediately afterward.
- **Audit display:** opening `/api/admin/audit-events` in the authenticated browser displayed `devices.registered`, `devices.associations.updated`, and `devices.product.assigned`, all successful and tied to the test record. Rejected operations did not appear as successful mutation records.

The association-conflict and missing-product responses are intentionally recorded as the generic “Invalid request.” Existing server error handling did not expose more specific validation text to the UI. The feedback is visible and rejection behavior was verified; no error-message or server response change was made in this verification-only work package.
