## 1. Executive summary

The HomeGrid software platform has a defined Firebase-backed registry, role-scoped server APIs, audit records, a deny-all Firestore client rule set and an emulator-only registry simulator. It does not expose any device communications contract or physical-device operation. Super Admin remains limited to platform administration and cannot operate appliances or household automation.

The earlier reported firmware state is now clarified by current authoritative records. FW-02A–FW-02F is accepted and cumulatively merged to Firmware `main` by PR #7. Its scope is host/mock-only: the output permission remains denied, the mock is the only actuator adapter, and FW-02 does not implement network, provisioning, MQTT, telemetry export, OTA or physical actuation. GitHub Actions run 38 passed for the final PR #6 head. The FW-02F handover explicitly says the PR #7 merge commit has no recorded check runs, so run 38 is not represented as a check on that merge commit. [FW-02F handover](https://github.com/Thangboiahi/HomeGrid-Firmware/blob/main/docs/FW-02F-final-handover-report.md) · [PR #7](https://github.com/Thangboiahi/HomeGrid-Firmware/pull/7)

The latest available firmware package is beyond FW-02: FW-03F is a planning/handover package. Its report says hardware/electrical evidence and cross-department acceptance remain open; its GPIO table is preliminary, and it does not authorize physical actuation. PR #14 is currently open as a draft. These planning artifacts do not establish a production interface. [FW-03F handover](https://github.com/Thangboiahi/HomeGrid-Firmware/blob/main/docs/FW-03F-final-integration-verification-handover.md) · [PR #14](https://github.com/Thangboiahi/HomeGrid-Firmware/pull/14)

**Readiness decision:** There is no approved shared device identity, provisioning, device-authentication, transport, message, telemetry, command, acknowledgement, fault-export, version-reporting or OTA contract available to implement against. Physical or production device integration is therefore **blocked pending cross-department decisions**. The software repository is ready to participate in contract definition and can continue its existing non-device emulator workflows. This review does not claim firmware/software integration testing.

## 3. Current software architecture and integration points

HomeGrid is one Next.js App Router application with Customer, Installer and Super Admin experiences. Browser pages submit same-origin requests; the browser does not authoritatively assign roles or permissions. Server code verifies the Firebase session, active account, permission and resource scope. Firestore client rules deny every read/write; trusted server operations use Firebase Admin through a `server-only` module and explicitly enforce authorization.

The main relevant software boundaries are:

| Boundary | Existing implementation | Integration relevance |
|---|---|---|
| Device registry | `DeviceDocument` in Firestore with product reference, kind (`simulated`/`physical`), registry state, timestamps and optional household/installation IDs. | It records HomeGrid software inventory and associations; its generated Firestore ID is not physical identity. |
| Product definitions | Server-managed product records with product code, display name and lifecycle. | A product reference does not define a firmware protocol or device capabilities. |
| Customer access | Household-membership checks in server services/routes. | Customer-visible devices are limited to authorized households. |
| Installer access | Explicit installation assignment checks. | Installer-visible devices are limited to assigned installations. Registry writes are not granted by the current permission matrix. |
| Super Admin | Platform registry/product/account/installation/diagnostic/audit operations. | No appliance-control or household-automation permission. |
| Audit | Server audit records for security-sensitive operations; device registry mutations use transactions that include their audit record. | Useful for software administration; not a device telemetry or command acknowledgement stream. |
| Simulator | `/super-admin/simulator` and `/api/dev/simulator/*`, gated to local Auth/Firestore emulators with matching demo project and loopback endpoints. | Registry-only; does not simulate connectivity, appliance state, firmware protocol or hardware. |
| Firmware releases | `/api/admin/firmware-releases` and `/api/admin/firmware-releases/:releaseId`, protected by `firmwareReleases.manage`. | Creates/approves/retires product/version-label metadata only. There is no firmware artifact store, device version report, signing, rollout or OTA operation. |
| Future boundary | `cloud-run/` is reserved and contains only `.gitkeep`. | No device backend, broker adapter or deployment service exists there. |

The full row-by-row firmware/software status and dependency matrix is in [integration-readiness-matrix.md](../architecture/integration-readiness-matrix.md).

## 6. Role and device-control security review

- **Customer:** can read devices only through verified household membership. No registry mutation or device command permission is granted.
- **Installer:** can read devices only within explicitly assigned installations. Existing installation workflow permissions do not authorize registry writes; no permission expansion was made.
- **Super Admin:** can perform the platform operations granted in the current matrix, including authorized registry and firmware-release metadata management. The role has no appliance operation, device command, appliance-state write or household-automation write capability.
- The existing human authentication session requires a recent ID-token authentication, same-origin session request and a five-day HttpOnly cookie with SameSite=Lax and Secure in production; protected verification checks revocation and active account/access state. Browser-supplied role or permission values are not authoritative.
- No API route for device command execution, relay/fan control, appliance-state writes, household-automation writes, telemetry ingestion or OTA was found in `src/app/api/`.
- The Admin SDK bypasses Firestore rules, so application authorization remains in the trusted server services/routes. No role or rule changes were made.

## 7. Production configuration, secrets and environment separation

### Firebase and isolation

- `.env.example` is emulator-only, selects `demo-homegrid`, uses loopback Auth/Firestore endpoints and documents that client Firebase values are public identifiers. It contains no real service credentials.
- `.firebaserc` defaults to `demo-homegrid`; `firebase.json` defines Auth/Firestore emulators and the local UI. The test scripts explicitly use `firebase emulators:exec --project demo-homegrid --only auth,firestore`.
- The emulator integration test overwrites Firebase environment values with demo project IDs and local endpoints and asserts emulator mode is rejected under `NODE_ENV=production`. Firebase Admin also checks matching client/server project IDs and uses ADC only outside emulator mode.
- Simulator gating additionally requires non-production mode, both emulator flags, a matching `demo-*` project, loopback hosts on ports 9099/8080 and successful local emulator connectivity. No production fallback is present in its service path.
- This confirms the repository's test configuration is isolated from production. No production project configuration, runtime environment, IAM policy or deployed service was inspected because none was used in this review.

### Secrets

- Admin SDK credentials are not bundled in application source: non-emulator use relies on ADC. The documented Cloud Run pattern is a least-privilege runtime identity, not a committed service-account key.
- `.gitignore` excludes `.env*` except `.env.example`, emulator data and logs. A repository scan found only `.env.example` among environment/credential-file name patterns, and no common private-key/service-account/API-secret token patterns in source/config files. This scan is a pattern check, not proof against every possible secret format.
- No production credentials or private keys were read, printed, created or used.

### Production readiness gaps

- The `cloud-run/` folder has no deployment assets beyond `.gitkeep`; there is no Dockerfile, Cloud Run service manifest, infrastructure-as-code or deployment pipeline in the reviewed repository.
- The current `.firebaserc` default is a demo project and `.env.example` is for local emulators. A controlled production environment template/variable contract, project selection procedure, Firebase Auth provider/domain settings, and release promotion procedure remain to be established. Do not copy emulator values into production.
- Production requires a dedicated Firebase project, enabled email/password provider and authorized domains as appropriate, `APP_ORIGIN` and matching client/server project identifiers, a least-privilege runtime identity/IAM grant for required Auth/Firestore operations, managed secret handling for any future secrets, and explicit deployment approval.
- `npm run start` is `next start`; the Node engine is constrained to `>=24.12.0 <25`. The production build uses `next build --webpack`. No dedicated health/readiness API route, Cloud Run health policy, centralized monitoring/alerting configuration, backup/restore plan or deployment rollback runbook was found. These must be designed and verified before production launch.
- Security-sensitive audit records are persisted in Firestore. The documented session audit fallback writes to server stderr/Cloud Logging if persistence fails; this fallback is diagnostic and is not a durable audit substitute.

- At the time of SW-01.6C, `README.md` described only SW-01.1 through SW-01.5, called `/auth` a preparation page with sign-in UI as future work, and described role pages as placeholders. The system overview also described its current milestone boundary as SW-01.1 through SW-01.5. These statements conflicted with SW-01.6A/B and were corrected during SW-01.6D.

## 9. Deployment prerequisites and risks

### Cross-department blockers for device integration

1. HQ/Architecture: approve physical identity, binding, lifecycle and shared contract ownership.
2. HQ/Security: approve provisioning, device authentication, credential/key lifecycle, TLS trust and recovery model.
3. Software/HQ: approve versioned transport, commands, acknowledgements, error/fault/telemetry schemas and firmware-version reporting.
4. HQ/Product: decide local/remote authority, command arbitration, restart and power-loss behavior.
5. Hardware: supply schematic/net/power/driver/feedback evidence and complete electrical/safety review; FW-03F says the present pin proposal is preliminary.
6. HQ: approve a separate implementation work package, authorization model, and acceptance/evidence plan after contract review.

### Production service blockers

1. Create/review production Firebase project settings and least-privilege runtime IAM outside this repository task.
2. Define Cloud Run packaging, runtime variables, release pipeline and rollback procedure; validate Node 24 server startup and secrets management in a non-production deployment first.
3. Add an operational health-check and monitoring/alerting plan; determine backup, restore and audit-retention requirements.
4. Review the final dependency audit before release; avoid the breaking forced Firebase CLI downgrade absent a safe compatible remediation.
