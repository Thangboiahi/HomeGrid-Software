# SW-01.7C — Account Suspension and Firebase Authentication Consistency

**Status:** Implemented and verified  
**Verification environment:** Node.js 24.12.0, npm 11.20.0, local Firebase Auth/Firestore emulators, project `demo-homegrid`

## 1. State machine

One current operation document is stored at `accountAccessOperations/{uid}`. It records `operationId`, `kind` (`suspend` or `reactivate`), `status` (`pending`, `processing`, `completed`, `manualReview`), requester UID/role, correlation ID, attempt and manual-retry counts, timestamps, lease information, last completed Auth step and a sanitized failure code. No credential, session token, raw Auth response or private key is stored. Audit documents use deterministic IDs for the operation request, each failure attempt, each explicit manual retry and completion.

| Phase | Firestore state | Firebase Auth action | Access |
| --- | --- | --- | --- |
| Active → suspension pending | One transaction sets `userAccess.state=suspended`, `users.accountState=disabled`, creates the outbox intent and `accounts.suspension.requested` event. | None before commit. | Denied immediately. |
| Suspension processing | Operation is claimed with an expiring lease and attempt count. | Disable Auth account, then revoke refresh tokens. | Denied throughout. |
| Suspension complete | One transaction marks the outbox complete and writes `accounts.suspended`. | Both Auth calls have succeeded. | Remains denied. |
| Suspended → reactivation pending | One transaction creates the intent and `accounts.reactivation.requested`; Firestore account records stay suspended/disabled. | None before commit. | Denied throughout. |
| Reactivation processing | Operation is leased and progress is recorded. | Enable Auth account, then revoke refresh tokens to invalidate old sessions. | Denied while Auth may already be enabled. |
| Reactivation complete | One transaction activates the access/profile records, completes the outbox and writes `accounts.reactivated`. | Both Auth calls have succeeded. | Active; old session cookies remain revoked. |
| Failure | Outbox records sanitized failure code and retry state; a failure audit event is written transactionally. | Retry repeats idempotent Auth calls. | Denied. |
| Terminal/manual review | Permanent Auth errors or five failed automatic attempts stop automatic processing. | No more calls until an authorized explicit retry. | Denied. |

## 3. Retry and processing behavior

The initial request transaction happens after `users.manage` authorization and target validation. Firebase Auth is never called before that transaction commits. The application APIs themselves retry a matching pending operation on a repeated authorized request. A five-minute processor lease lets another request reclaim work after process termination. Automatic retry uses five attempts with exponential backoff starting at 30 seconds and capped at one hour. `auth/user-not-found`, `auth/insufficient-permission`, `auth/invalid-uid` and `auth/operation-not-allowed` enter `manualReview` immediately; other failures enter manual review after the attempt limit.

An authorized Super Admin can explicitly restart a terminal operation by repeating the matching API request with `{"retryManualReview":true}`. The manual retry is audited and resets the automatic attempt round while retaining the same operation ID. Repeated requests for an already-completed, state-consistent operation return that operation without a duplicate request or completion event. If Auth state has drifted, a new reconciliation operation is created while first restoring denied Firestore state.

The local operator command is `npm run process:account-access-operations:demo`. It starts only Auth/Firestore emulators under `demo-homegrid`; the script independently enforces the demo project and loopback endpoints. No scheduler or Cloud Run worker was deployed, and no production resource or operation was accessed. In a deployed application, pending work can be retried through the existing protected account APIs; pending/manual-review status and sanitized failure codes are visible in the Super Admin managed-account read.

## 4. Authorization and idempotency

Every protected request verifies the signed session, then checks the server-managed `userAccess`, `users` and `accountAccessOperations` records. Any pending/processing/manual-review operation is denied. A completed suspension remains denied. Reactivation keeps both Firestore account records denied until its final transaction, and Auth refresh tokens are revoked before that transaction. Active accounts without an unfinished operation follow the existing permission matrix.

The per-UID outbox serializes repeated requests for the same desired transition. One logical operation ID and correlation ID persist through Firestore retries and external retries. Deterministic audit event document IDs prevent duplicate request/completion events. A different opposite operation conflicts while a prior operation is pending or in manual review. A completed transition to the opposite state creates a new operation ID. This is a domain-specific idempotency boundary; it does not introduce a general `Idempotency-Key` API.

## 6. Remaining limitations

- No background production scheduler/queue or Cloud Run service is deployed. Retry is operator-driven through the protected endpoints; this keeps this package within the current application architecture but requires an operational owner to monitor pending/manual-review accounts.
- The outbox keeps one current operation per UID; append-only audit events preserve request/failure/completion history. Outbox retention and audit retention remain operational policy decisions.
- Auth calls are idempotently repeated after uncertainty. Firebase Auth and Firestore do not share a distributed transaction; the outbox and fail-closed Firestore states provide recovery and safe access behavior.
- Session sign-out remains its previously documented Auth-revocation-plus-audit sequence and is outside this package.
