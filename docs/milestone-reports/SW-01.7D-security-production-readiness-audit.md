## Privileged mutation and audit consistency

Inspection of the production service write sites found that Firestore business mutations in `protected-operations.ts` use the shared `runAuditedTransaction` runner. It prepares the audit record and reference once outside Firestore's retry callback and commits the event with the business write. The bootstrap script similarly stages its marker, initial access records and audit record in one transaction. Emulator tests verify atomic failure, a single logical audit event after transaction retries, and denial without mutation/a success event.

The suspension/reactivation outbox uses stable operation IDs and deterministic request, attempt, manual-retry and completion event IDs. Its Firestore intent and request audit commit together; completion state and completion audit commit together. Failure state and its failure event are also written together. If failure persistence itself cannot commit, the processor emits a credential-free server log and leaves the operation recoverable after lease expiry. The audit found that Firestore finalization errors had previously been mislabeled as Auth errors. This is corrected and regression-tested.

### Idempotency and retry boundaries

- Firestore transaction callback retries reuse the prepared event ID and event data for one logical call.
- Repeated matching HTTP requests resume the one per-UID pending operation; completed consistent operations return without duplicate request/completion records. Opposite transitions conflict while an operation is pending or in manual review.
- External Auth calls are repeated after uncertainty. Disable/enable and refresh-token revocation are same-direction operations and are treated as idempotent. There is no general-purpose HTTP idempotency-key facility.
- A five-minute lease and fencing token prevent stale processors from committing progress or completion to Firestore. An already-issued Auth request cannot be cancelled by lease expiry. A slow or partitioned request could overlap a recovered same-operation request; the repeated Auth calls have the same desired state, and the lease token fences stale Firestore writes. This is a residual concurrency limitation, not a proven distributed lock over Firebase Auth.
- Failure audit IDs are deterministic for each automatic attempt/manual-retry round. A repeated attempt cannot create multiple records for the same phase attempt.

## Account suspension and reactivation review

The request transaction requires `users.manage`, validates the target, denies self-targeting, persists the operation and audit, and puts HomeGrid access into a denied state before Firebase Auth is called. Reactivation likewise begins with Firestore access denied; only after Auth enablement and refresh-token revocation does the final transaction restore active Firestore state alongside its completion audit. Authorization checks `userAccess`, `users` and the operation state server-side before allowing protected access. Failure/manual review does not restore access.

Retries are bounded to five automatic attempts with backoff; permanent Auth failures and exhausted retries enter manual review. A matching manual retry requires the existing `users.manage` authorization and is audited. The emulator suite covers denied access during Auth failures, Auth enable/revocation failures, retry, lease recovery, operation conflicts, manual review and audit commit failure. It does not establish a hard upper bound on total duration of every external Auth request; the lease caveat above remains.

## Session revocation review

Session creation enforces a configured same-origin request, requires recent Firebase authentication (maximum age five minutes), establishes an HttpOnly cookie with five-day expiry, sets Secure in production and uses the existing SameSite policy. The cookie contains a signed Firebase session; role and permissions are loaded from server-managed Firestore records. Firebase Admin credentials remain server-only.

Sign-out verifies the cookie with revocation checking, waits until the session is older than Firebase's second-granular revocation cutoff, calls `revokeRefreshTokens`, then appends `auth.session.ended`. The browser clears its cookie in both success and failure responses. On failure it receives HTTP 503 and the UI says invalidation could not be confirmed, asking the user to retry. No client role assignment or appliance authorization was found in this flow.

**Deferred audit gap at SW-01.7D:** if Auth revocation succeeds but the separate audit append fails, the route returns 503 and clears the local cookie, but the already-revoked cookie cannot pass the subsequent revocation-checked verification to recover its UID. Retrying therefore cannot reliably backfill the missing success event. If Auth revocation itself fails, the response is 503 but this route does not persist a failure audit event. The behavior does not restore access and does not claim confirmed completion, but audit completeness and retry recovery are not guaranteed for sign-out. SW-01.8A subsequently replaces this sequence with a durable intent/outbox workflow.

Minimum robust remediation, if sign-out audit completeness is required, is a durable intent/outbox committed before revocation with a stable operation identity, followed by retryable Auth revocation and a completion/failure audit. A stable identifier must not be derived from or store the raw session cookie. This would be a targeted session workflow change and should be separately scoped; this audit did not introduce it.

## Cross-role boundaries

- **Customer:** authorization and the protected data services enforce membership in the requested household before accessing its devices; unrelated resources are concealed. Customer registry writes are absent from the permission matrix and rejected by protected APIs.
- **Installer:** installation data and mutation services verify the caller's assigned installer UID. An installer cannot perform registry writes under the current role grants.
- **Super Admin:** platform permissions cover accounts, product definitions, device registry, installations, firmware release metadata, diagnostics and audit records. The role has no household authorization and no appliance-control, device-command, appliance-state-write or household-automation-write permission. No corresponding control route was found in the route inventory.
- **Client/database boundary:** client-supplied role or ownership fields are not authoritative. Firestore Security Rules remain deny-all for browser reads and writes; Admin SDK operations are confined to server-only code.

The existing role security emulator suite passed tests for household and installation isolation, user provisioning, registry authorization, and Super Admin platform metadata without appliance-control permission. The focused permission tests also verify prohibited capabilities are absent.

## Monitoring and production operations

No production worker, scheduler, alert, deployment or monitoring configuration is present or was created. Before operating these workflows in production, an operational owner should monitor:

- age and count of `pending`/`processing` account-access operations, expired leases and `manualReview` records;
- failures by `lastFailurePhase` and sanitized `lastFailureCode`, plus operation attempt count and time since last progress;
- denied authorization and repeated 401/403/409/503 outcomes, without logging cookies, ID tokens, credentials or raw Auth errors;
- `homegrid.security_audit.persist_failed` and `homegrid.account_access.failure_persistence_failed` structured server events, with alerting and an escalation path;
- divergence between Auth disabled state and Firestore account state, and backlog/latency of any future processor.

`lastFailurePhase` is stored in the server-only operation document and is not currently included in the managed-account API response; operational monitoring must query it through a trusted backend/administrative channel, never expose the outbox to browser Firestore access, and must not return raw Auth errors or credentials.

The emulator regression produced non-blocking Firebase Admin metadata-lookup timeout warnings. The runs succeeded, and the Firebase CLI explicitly identified `demo-homegrid` as a demo project. No production project or credentials were used.
