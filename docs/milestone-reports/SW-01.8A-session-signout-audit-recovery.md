# SW-01.8A — Durable Session Sign-out and Audit Recovery

**Status:** Implemented and verified  
**Verification environment:** Node.js 24.12.0, npm 11.20.0, Firebase Auth/Firestore emulators, project `demo-homegrid`  
**Production resources:** None accessed

## 1. Workflow and state machine

The sign-out endpoint checks same-origin protection, then uses the signed session cookie's SHA-256 digest as the stable opaque `operationId`. The digest is not sufficient to authenticate to HomeGrid; its only purpose is to locate the durable server-side operation. The raw cookie, ID token, refresh token and Firebase credentials are never stored.

| Phase | Durable Firestore state | Firebase Auth | Access behavior |
| --- | --- | --- | --- |
| Intent | Transaction creates `sessionSignOutOperations/{operationId}` and `auth.session.sign_out.requested` audit event. | No call before transaction commit. | Server authorization sees the matching operation and denies that exact session. |
| Processing | Claim transaction sets `processing`, increments attempt count and assigns a one-minute lease/fencing token. | Revoke refresh tokens outside Firestore transaction. | Denied while pending or processing. |
| Failure | Transaction stores sanitized phase/code, retry time and deterministic per-attempt failure audit; status returns to `pending` or terminal `manualReview`. | Failure is not reported as success. | Denied while the operation exists. |
| Completion | One Firestore transaction sets `completed` and writes `auth.session.ended`. | `revokeRefreshTokens` returned successfully first. | Firebase revocation rejects the old cookie; the outbox also remains a denial boundary. |

Repeated processing is safe: Firebase token revocation is repeated for the same UID, only one active lease can claim an operation, stale lease owners cannot commit, and the deterministic completion event ID prevents duplicate logical completion. A completion/audit commit error leaves the operation retryable; the next attempt repeats revocation before trying the final transaction again.

## 2. Schema and transaction boundaries

`sessionSignOutOperations` contains: opaque `operationId`, UID, numeric Auth time, actor role, status, attempt count, manual-review count, correlation ID, retry/lease timestamps and tokens, last sanitized failure phase/code/time, and completion time. It contains no token, cookie, password, credential or raw Auth response. Client Firestore rules remain deny-all.

Transaction boundaries:

1. Intent document and request audit event commit atomically before any Auth call.
2. Lease claim and attempt increment commit atomically.
3. Failure state and its deterministic per-attempt failure audit commit atomically.
4. Completion status and completion audit commit atomically after Auth confirms revocation.

Auth and Firestore do not provide a distributed transaction. If Auth succeeds and Firestore finalization fails, the durable operation is retried and Auth revocation is repeated. Audit staging/persistence failure is logged without credentials; an unavailable Firestore cannot guarantee a failure record until a later retry succeeds.

## 3. Authorization and browser retry

Session sign-out is a self-service operation and does not grant or alter a role. New intent requires a Firebase-signed session cookie and same-origin request. Protected authorization verifies the session with revocation checking and checks the outbox document for that exact cookie digest; any existing sign-out operation denies it. No role, resource scope, appliance permission or account state is restored by the processor.

The browser always clears its HttpOnly cookie. When the server returns a retryable 503 after storing intent, it includes the opaque operation ID; the client keeps only that ID in `sessionStorage` and sends it on the next same-origin DELETE retry. The server only processes an existing operation for this recovery path. Successful completion clears the stored ID. An operation ID can cause only repeat revocation for its bound UID; it cannot authenticate or authorize any other HomeGrid action.

Invalid cookies with no matching operation simply clear locally. An existing operation is looked up by digest before cookie verification, so a revoked or expired cookie can still identify prior durable work. The emulator tests exercise revoked-cookie duplicate requests and explicit opaque-ID retry; they do not wait for a real five-day session expiry.

## 4. Retry and operational recovery

Automatic retry state is bounded to five attempts with exponential backoff starting at 30 seconds and capped at one hour. Permanent Auth errors or exhausted attempts enter terminal `manualReview`. A one-minute lease allows recovery after a processor interruption and fences concurrent/stale Firestore writes. The test suite injects a shorter retry base to verify the retry paths quickly.

`processPendingSessionSignOutOperations()` is a server-only processor entry point. The provided `npm run process:session-signouts:demo` command is hard-guarded to `demo-homegrid` and local loopback emulators. At the time of SW-01.8A no production worker, scheduler, Cloud Run service or manual-review retry endpoint was deployed. SW-01.8D later added a same-origin, `users.manage`-protected operator retry endpoint; production retry ownership and monitoring still require approval before production use.

If Firestore cannot commit the initial intent, the service intentionally does not call Auth. The route still clears the browser cookie and returns 503, but there is no durable operation to retry; the user must authenticate again and initiate sign-out once persistence is available. A copied cookie may remain valid until a later successful revocation or expiry. This is the fail-closed ordering required to avoid an unrecorded Auth mutation and is an infrastructure-availability limitation.

## 8. Remaining limitations and completion boundary

- Production scheduling/worker ownership and alerting are not included; the local processing script is demo-only.
- `manualReview` is terminal for this work package; there is no operator retry API.
- Initial Firestore intent failure prevents revocation and cannot be recovered from an outbox that could not be written. The client cookie is nevertheless cleared and the response is not success.
- The emulator suite does not wait for a real expired session cookie; it covers invalid-cookie clearing and recovery by operation ID after revocation.
- No production Firebase project, credentials, users or operations were accessed. Firestore client rules, role permissions, authentication architecture and appliance/firmware boundaries remain unchanged.
