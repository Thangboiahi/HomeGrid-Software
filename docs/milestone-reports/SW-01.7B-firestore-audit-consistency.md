# SW-01.7B — Firestore Privileged Mutation and Audit Consistency

**Status:** Implemented and verified  
**Verification date:** 2026-11-08  
**Environment:** Node.js 24.12.0, npm 11.20.0, Firebase Auth and Firestore emulators, project `demo-homegrid`

## 1. Summary

Firestore-only privileged mutations in the audited operation inventory now commit their business data and success audit record in a single Firestore transaction. A failure to stage or commit the audit write aborts the associated mutation. Existing authorization, Firestore rules, device restrictions and role permissions were preserved.

## 4. Transaction and retry approach

The service performs authorization and input validation before transaction entry, then reads all required Firestore state before scheduling writes. The shared audit runner creates one audit reference and builds the event record once per service invocation, outside the Firestore retry callback. The business callback schedules its writes, and the helper stages the audit with `transaction.create`. Firestore commits both writes together or neither.

The audit schema remains unchanged: actor UID/role, action, resource type/ID, outcome, correlation ID and server timestamp. Existing correlation IDs supplied by service context are preserved. No external Firebase Auth calls occur inside the retryable Firestore callback.

Firestore callback retries reuse the same audit reference and event record, avoiding duplicate audit documents for one logical callback-retried operation. This does not deduplicate a separate HTTP retry after a lost response. An idempotency-key/receipt API would require a separately approved contract and remains a known limitation for generated-ID resource creation.

## 5. Failure and security verification

The focused emulator suite verified:

- Successful provisioning, product create/state, firmware release create/state, Installer assignment and installation progress/completion each have exactly one matching success event.
- Concurrent product state transitions yield one success and one rejected stale transition, with one durable state-change event.
- Business validation failure leaves business data unchanged and creates no success event.
- Injected audit-staging failure leaves the business mutation and success event absent; a separate real emulator commit conflict caused by an occupied audit document ID also rejects the transaction and leaves the business mutation absent.
- Simulated transaction callback retry keeps the same audit reference/correlation identity and stages a single audit create per committed transaction attempt.
- Installer mutation is denied under the current permission matrix and cannot produce a misleading success event.
- Existing security integration suite continues to enforce Customer household scope, Installer assigned-installation scope, Super Admin platform-only permissions, and no appliance-control capability.
- Emulator integration confirms configuration is isolated to `demo-homegrid` and local Auth/Firestore endpoints.

No role permissions, Firestore rules, API authorization policy, device controls, MQTT or firmware integration were changed.

## 7. Limitations and deferred work

- Account suspension still spans Firestore and Firebase Auth without a durable outbox/retry state machine. Its existing Firestore access/profile update remains an atomic batch, but the whole workflow is not distributed-atomic. SW-01.7C owns the outbox and suspension retry design. Reactivation was not introduced.
- Session sign-out token revocation and its audit append remain a cross-system sequence outside this Firestore-only package.
- A new HTTP request retry is distinct from a Firestore transaction callback retry. Generated-ID create operations do not yet have an idempotency receipt contract, so an ambiguous network response can still lead a caller to retry and create another resource.
- The retry test deterministically simulates the Firestore SDK invoking the callback again; separate concurrent transition behavior is exercised against the emulator.
- Firebase metadata lookup warnings are environmental and non-blocking in this local emulator run.

## 8. Exclusions and completion boundary

No account-suspension outbox, reactivation, production resource operation, permission expansion, Firestore-rule change, appliance-control capability, MQTT, telemetry, physical-device integration or firmware communication was introduced. SW-01.7B is complete; do not begin SW-01.7C without separate authorization.
