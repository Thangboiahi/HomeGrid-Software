# SW-01.4 Final Integration and Verification

**Status:** Integrated verification complete; acceptance recommendation: accept with the browser-level workflow review deferred.
**Scope:** SW-01.4A through SW-01.4D. No SW-01.5 work is included.
**Verified with:** Node.js 24.12.0, npm 11.20.0, Firebase Auth and Firestore emulators using `demo-homegrid`.

## Domain model and validation

`DeviceDocument` remains a Firestore record with a generated document ID. Its required application fields are `productDefinitionId`, `kind`, `state`, `createdAt`, and `updatedAt`. `kind` is `simulated` or `physical`; `state` is the registry lifecycle value `unassigned`, `assigned`, or `retired`. `householdId` and `installationId` are optional non-empty identifiers. No hardware identity, connectivity, telemetry, or provisioning fields are defined. The record ID is not proof of physical-device identity.

Validation in `src/validation/device.ts` checks required fields, classification, lifecycle vocabulary, timestamp shape, and optional association identifiers. Unknown lifecycle values are rejected. Household-only and installation-only associations are supported. When a device has both associations, the installation must reference the same household. Cross-household reassignment is rejected. A record whose installation lacks a household reference cannot be combined with a household association because consistency cannot be established.

Registry lifecycle and operational health are separate. The current states describe registration only; they do not mean online/offline or healthy/unhealthy. No device retirement or reactivation operation is available. The transition policy remains deferred pending an approved domain decision.

## Registry services and authorization

Trusted services in `src/services/security/protected-operations.ts` perform authorization and business validation even when a route checks permission first. Device registration requires `devices.register` and an active product definition. Household/installation association and product reassignment require the existing `devices.assign` permission; product reassignment also requires `products.manage`. Product reassignment requires an active product definition. Retired records are not mutable through these workflows.

The current permission matrix grants registry writes only to Super Admin. Customer reads require household membership. Installer reads require an explicit installation assignment. Super Admin is platform-scoped and has no household appliance authorization. No role receives appliance command, appliance-state write, or household-automation write capabilities.

## API inventory

| Method and path | Purpose and boundary |
| --- | --- |
| `GET /api/customer/households` | Lists the signed-in customer’s member households. |
| `GET /api/customer/households/:householdId` | Reads one household after membership verification; unrelated resources are concealed. |
| `GET /api/customer/households/:householdId/devices` | Lists devices for a verified member household. |
| `GET /api/devices/:deviceId` | Reads a device for its household member, assigned installer, or authorized platform reader. |
| `GET /api/installer/installations` | Lists installations assigned to the installer. |
| `GET /api/installer/installations/:installationId` | Reads an assigned installation. |
| `GET /api/installer/installations/:installationId/devices` | Lists devices within that assigned installation. |
| `GET /api/admin/devices` | Lists platform registry records for authorized readers. |
| `POST /api/admin/devices` | Registers a simulated or physical-classified software record. |
| `POST /api/admin/devices/:deviceId/assignment` | Associates household and/or installation within validated scope. |
| `PATCH /api/admin/devices/:deviceId/product` | Reassigns the product definition with both device-assignment and product-management permissions. |

The Super Admin view also reads product definitions through the existing protected products API. There is no device lifecycle mutation endpoint.

## Audit behavior

Device registration, household/installation association, and product reassignment write their audit event in the same Firestore transaction as the device mutation. Firestore transaction retries preserve atomicity, and integration coverage verifies that a failed audit write does not leave a device mutation committed. Successful audit entries carry the actor UID and role, action, resource, outcome, correlation ID, and server timestamp. The client Firestore rules continue to deny all reads and writes.

## Role interfaces

- **Customer:** displays devices belonging to authorized households, including product and registry metadata; it has no registration or mutation controls.
- **Installer:** displays device records from explicitly assigned installations and is read-only for the registry.
- **Super Admin:** displays the platform registry, search/filter, registration, product reassignment, and household/installation association workflows. Lifecycle state is informational.

All role pages call the server-side page-role guard. API routes and services independently authorize requests, so hiding a control is not the security boundary. The browser uses same-origin APIs; it does not read Firestore directly or submit authoritative roles, ownership, or assignment decisions.

## Browser review and known limitations

The local production server started on `127.0.0.1:3000`, but the available in-app browser could not connect to the loopback URL (`ERR_CONNECTION_TIMED_OUT`). The `/auth` page is still a milestone placeholder and does not provide an interactive sign-in flow. Therefore, no browser-level authenticated review of device registration, product reassignment, association forms, searching, empty/error feedback, or responsive layouts is claimed. Two server-rendered component tests verify role-specific content and the absence of registry controls for Customer and Installer; API/emulator tests verify the underlying operations and permissions.

The current npm install policy skipped three dependency lifecycle scripts. The requested unit/integration tests, lint, typecheck, and production build all passed despite that warning. The dependency tree should be reinstalled with the repository’s approved npm script policy in a normal developer environment if those hooks are required for other local workflows.

`npm audit` reported 20 moderate affected dependency entries, all in development/tooling dependency graphs. The reported advisory families are OpenTelemetry Core (GHSA-8988-4f7v-96qf), glob (GHSA-3g3m-2fjr-6pw4), minimatch (GHSA-g3hv-75wg-m249), and uuid (GHSA-w5hq-g745-h8pq). npm’s suggested forced resolution downgrades `firebase-tools` to 13.11.2, a breaking major downgrade, so no upgrade was applied. `npm audit --omit=dev` reported zero production vulnerabilities. No high or critical advisories were reported.

## Integration boundaries and dependencies

SW-01.4 adds no MQTT, physical ESP32 communication, telemetry ingestion, appliance commands or state writes, household automation, firmware transport, OTA, hardware provisioning, or physical-device identity assumptions. Existing firmware-release functionality remains metadata-only and was not changed; no firmware transport contract exists. Any future device communication requires HomeGrid HQ approval of its integration contract, including MQTT over TLS details.

## SW-01.4D correction

Final review found that a device with a household association could be linked to an installation with no household reference, making a combined relationship impossible to verify. `assignDevice` now rejects that combination; independent associations remain valid. An emulator regression verifies the mutation and its audit event are both absent after rejection.

## Acceptance recommendation

Recommend accepting SW-01.4’s server/domain/API integration and automated verification. Defer visual/browser acceptance until a browser can reach the local app and role sessions can be exercised; this is an environment/UI availability limitation, not a passed browser test. The device lifecycle transition policy remains unresolved and deferred. Do not begin SW-01.5 until this report is reviewed.
