# SW-01.5 — Software Device Simulator

**Status:** Implementation complete; final verification recorded after emulator regression.
**Boundary:** Local development and tests only. No SW-01.6 work is included.

## Architecture

The simulator is isolated under `src/domain/simulator`, `src/services/simulator`, `src/validation/simulator.ts`, `src/features/device-simulator`, and `/api/dev/simulator`. It uses the existing `DeviceDocument` and `kind: simulated`. It does not add a simulator-specific device field or collection. Existing `registerDevice`, `assignDevice`, `reassignDeviceProduct`, `readRegisteredDevices`, permission checks, validation, and audit transactions remain the registry authority.

`getSimulatorEnvironment` enables the simulator only when:

- `NODE_ENV` is not production;
- client and Admin SDK emulator flags are both enabled;
- client and Admin project IDs match and start with `demo-`;
- Auth and Firestore hosts are loopback addresses on ports 9099 and 8080;
- public client endpoints match those server endpoints.

`assertSimulatorEmulatorsReady` opens TCP connections to both configured ports before simulator reads or writes. It does not initialize Firebase if any environment check fails. There is no production fallback. Page access is also hidden outside this environment.

## Domain and operations

Simulated records retain the normal required fields: generated Firestore software-record ID, active `productDefinitionId`, classification, registration state and timestamps. Optional household and installation associations use the existing registry validation. Combined associations must match the installation household. Creation with associations reads and validates product/household/installation references in the same transaction that writes the device and its `devices.registered` audit event. Association changes and product reassignment continue to use their existing atomic mutation/audit transactions.

Supported operations:

- create simulated devices with optional household and/or installation association;
- retrieve only records classified `simulated` through the simulator listing;
- update associations and product definitions through the existing protected services;
- search and filter simulator records in the development console;
- create keyed test fixtures with duplicate-key prevention and clean only those fixture IDs and audit events from a verified emulator.

Fixture cleanup is not exposed as an API or UI action. It requires `HOMEGRID_SIMULATOR_TEST_CLEANUP=true`, the non-production demo emulator configuration, reachable local emulator ports, and a fixture object that tracks each created ID. It refuses to delete a record whose classification is not `simulated`.

## API inventory

| Method and path | Operation |
| --- | --- |
| `GET /api/dev/simulator/devices` | List simulated registry records for an authorized platform user. |
| `POST /api/dev/simulator/devices` | Create a simulated record; physical classification supplied by a client is rejected. |
| `POST /api/dev/simulator/devices/:deviceId/assignment` | Associate a simulated record with a household and/or installation. |
| `PATCH /api/dev/simulator/devices/:deviceId/product` | Reassign a simulated record to an active product definition. |
| `/super-admin/simulator` | Development-only console; Super Admin page guard plus environment gate. |

There is no simulator DELETE endpoint and no lifecycle mutation endpoint. Test cleanup is isolated to the emulator test helper.

## Role boundaries

- **Customer:** may read simulated devices only through existing household membership-scoped routes; simulator list and mutation endpoints deny Customer.
- **Installer:** may read simulated devices only through existing assigned-installation routes; simulator list and mutation endpoints deny Installer.
- **Super Admin:** may use the simulator only in a safe local emulator environment, and only for operations granted by existing `devices.read`, `devices.register`, `devices.assign`, and `products.manage` permissions. No permissions were added.

Super Admin remains separate from household operation. There are no device command, appliance-state, relay, fan, automation, or control endpoints.

## Simulation and integration limits

The simulator models registry presence and associations only. `unassigned`, `assigned`, and `retired` keep their registry meanings; the simulator adds no lifecycle transitions. Records display a visible `SIMULATED` classification. Physical records remain `kind: physical` and are not returned by the simulator list.

No MQTT, ESP32, device-to-cloud communication, telemetry, sensor or relay data, online/offline state, appliance state simulation, firmware communication, OTA, hardware provisioning, credentials, or hardware identity were added. There is no simulator wire protocol or firmware contract. Future physical-device integration requires HomeGrid HQ approval.

Known limitations: this is a registry workflow simulator, not a device behavior simulator. Association references are entered as IDs and validated by server services. Simulator listing reuses the registry reader and its existing result limit. Fixture key deduplication is scoped to one fixture-manager instance; cleanup is limited to IDs that instance created and is available only from the emulator test helper. There is no user-facing fixture removal or association-clearing workflow. Lifecycle transitions remain unexposed and deferred under the existing unresolved policy.

The repository directory did not contain a `.git` metadata entry during final inspection, so a Git diff/status comparison was unavailable. The workspace file structure and simulator-related implementation/docs were inspected directly. A targeted scan for common private-key and credential token patterns outside generated/vendor directories returned no matches. Emulator configuration is ignored by `.gitignore`; it was generated under `.firebase/config` for local CLI use.

No SW-01.6 work was started. SW-01.5 is ready for review; its acceptance does not imply approval of firmware or physical-device integration.
