## 3. Final security audit

### Authentication and account lifecycle

- Session creation checks a same-origin request, requires an ID token authenticated within five minutes, validates the active server-managed account/access record, then issues a five-day `HttpOnly`, `SameSite=Lax` cookie with `Secure` in production.
- Protected requests verify the signed cookie with revocation checking and re-read the Firebase Auth user, profile and `userAccess` record. Disabled or suspended accounts and missing/inactive access are rejected; client claims/fields do not supply the authoritative role.
- Public registration creates a Firebase Auth identity only. Customer/Installer access is provisioned by a permission-checked Super Admin operation; Super Admin is not assignable through that flow. The first Super Admin uses a trusted one-time operator bootstrap.
- Sign-out attempts refresh-token revocation, writes an audit event and clears the browser cookie. If revocation fails, the endpoint returns a failure status while clearing the local cookie; copied-cookie invalidation is not claimed when revocation did not succeed.
- The emulator authentication suite passed tests for unprovisioned identities, inactive access, server-derived role routing and logout revocation.

### Authorization and resource isolation

- Customer household and device reads require current household membership. Cross-household resources are concealed as not found.
- Installer reads and permitted installation workflow updates require the actor's explicit assignment; registry writes are absent from Installer grants.
- Super Admin is limited to permissions in the explicit matrix. The prohibited capabilities `appliances.operate`, `devices.commands.execute`, `appliances.state.write` and `householdAutomation.write` are not granted.
- Routes and trusted services both authorize. The browser does not decide its role, and service methods do not rely solely on hidden interface controls.
- Emulator tests passed customer/installer isolation, stale/suspended-account rejection, unauthorized registry denials, client role/ownership manipulation and Super Admin permission-boundary cases.

### Firestore, input validation and simulator

- Firestore rules deny all browser reads and writes, including `userAccess` and audit data. Admin SDK calls bypass these rules and therefore depend on server service authorization.
- Device registration and association/product reassignment validate the product and association references, preserve the simulated/physical classification, and do not treat a Firestore record ID as physical identity.
- The simulator requires non-production mode, matching demo project IDs, both emulator flags, loopback Auth/Firestore hosts and reachable local emulator ports. Test scripts force `demo-homegrid` and emulator endpoints. Its data is registry-only.
- Session request body size/content type and JSON shape are bounded; route and domain validation reject malformed values. No hardware protocol or device-control interface is present.

### Audit integrity — deployment blocker

Device registration, device association and device product reassignment write the corresponding audit record within the same Firestore transaction as the mutation. Their emulator tests verify atomic behavior.

Several other privileged mutations do not use that pattern. In `src/services/security/protected-operations.ts`, the Firestore mutation or batch is committed before the separate `auditContext` call for installation progress/completion, installer assignment, product creation/state changes, firmware-release metadata creation/state changes, account provisioning and account suspension. If the audit write fails, the API can return an error after the business mutation has committed, leaving no Firestore audit event. Account suspension also spans Firestore and Firebase Auth, so those stores cannot be updated atomically by the current implementation; a failure between steps can leave partial state. The current security integration tests do not cover audit-write failure for these operations.

`recordAuditEvent` emits a credential-free stderr fallback and rejects on persistence failure. That protects callers from receiving a success result when audit persistence failed, but it cannot undo mutations already committed by the operations listed above. Treat this as a production security and operational blocker. A follow-up should define failure/compensation semantics and add failure-injection tests before changing the mutation flow. This audit did not change application code or weaken existing checks.
