# SW-01.8D — Audited Session Sign-out Manual-Review Recovery API

**Status:** Implemented and verified  
**Date:** 2026-11-09  
**Environment:** Local Auth/Firestore emulators, project `demo-homegrid` only  
**Production resources:** None accessed

## Existing behavior inspected

- The server-only `sessionSignOutOperations` record binds its opaque operation ID to one immutable UID. Its existing fields include `status`, `attemptCount`, `manualReviewCount`, `correlationId`, lease/retry fields and sanitized failure metadata. The operation schema has no separate `manualRetryCount`; `manualReviewCount` is initialized by the existing coordinator.
- `processPendingSessionSignOutOperations()` delegates to the existing SW-01.8C bounded processor. It discovers due pending and expired processing operations. `process(operationId)` claims through the existing one-minute lease/token transaction, waits until revocation is valid for the stored auth time, and invokes only `revokeRefreshTokens(operation.uid)`. Existing transaction/audit handling persists failures or completion.
- Once status is `manualReview`, the processor does not claim it. There is currently no operator recovery method or HTTP route for session sign-out manual review.
- The session request, per-attempt failure and completion audit records use the existing `auditEvents` schema, operation-based deterministic document IDs and Firestore transactions. Audit metadata supports actor UID/role, action, resource, outcome and correlation ID; it has no reason/reference field. This change will not expand that schema or accept a free-text reason.
- `requirePermission("users.manage", cookie)` verifies the active server session and server-derived role; the existing permission grant is held by Super Admin. Admin mutation routes call `assertTrustedMutationOrigin` before permission checks. Dynamic Route Handler parameters use the current Next.js promise-based `context.params` convention.
- SW-01.8A established durable self-service sign-out and processor/audit boundaries. SW-01.8B deferred operator recovery and production operation. SW-01.8C added bounded indexed processing, leases/heartbeats and emulator-only worker execution.

## Proposed minimal change

Add one narrow `retryManualReview(operationId, actor)` transaction to the existing session-sign-out coordinator and a server-authorized service wrapper. Add `POST /api/admin/session-signouts/{operationId}/retry` using the repository’s same-origin and `users.manage` controls. The transaction will proceed only from `manualReview`, preserve the operation ID and UID, reset the automatic attempt count and transient failure/lease data, schedule it as due `pending`, increment the existing `manualReviewCount`, and create `auth.session.sign_out.retry-requested` at a deterministic retry-round audit ID. Duplicate/concurrent requests will observe the new pending state and cannot create another logical event. The HTTP handler will not call Firebase Auth; only the existing bounded processor will perform revocation.

No reason/reference field will be added because the current audit schema does not support it. No changes are planned to Firestore rules, roles, account-access processing, device controls or production deployment.

## Implementation delivered

### Endpoint contract

`POST /api/admin/session-signouts/{operationId}/retry` is a Node.js Route Handler using the current promise-based dynamic route parameter convention. It accepts no request body and validates the operation ID as a lowercase 64-character digest. Results:

| HTTP status | Behavior |
| --- | --- |
| `202` | Manual-review record was atomically requeued. Returns operation ID, pending status and `manualReviewCount`. |
| `200` | Completed record is unchanged and reported as already completed. |
| `400` | Invalid digest or any request body, including a client-supplied UID. |
| `401` | Missing/invalid active server session. |
| `403` | Untrusted origin or operator lacks `users.manage`. |
| `404` | Operation does not exist or has a mismatched stored operation ID. |
| `409` | Operation is already pending or processing; active state/lease is untouched. |
| `500` | Firestore/audit transaction failure; transaction rollback leaves the operation in manual review. |

### Authorization, transaction and audit

The route validates `Origin` through `assertTrustedMutationOrigin`; the service independently requires `users.manage`. The actor UID and role come from the verified active session. Permission denial happens before operation lookup, so unauthorized callers do not learn operation status. Current grants give `users.manage` to Super Admin; the permission matrix was not changed.

The server-only coordinator transaction reads the existing record and proceeds only from `manualReview`. It preserves operation ID, bound UID, initiating actor and correlation ID; resets `attemptCount` to zero for a new bounded retry round; increments the existing `manualReviewCount`; sets `nextAttemptAt` to now; clears lease and failure fields; and creates `auth.session.sign_out.retry-requested` in the same transaction. The deterministic event ID is `{operationId}-manual-retry-{manualReviewCount}`. A state conflict or audit staging/commit failure cannot produce a successful state-only mutation.

No reason/reference is accepted. The existing audit schema does not include that metadata, and no schema expansion was approved. No raw credentials, cookies, tokens, Auth responses or target UID are returned or logged by this endpoint.

### Idempotency and processor integration

Repeated pending and processing requests return `409`; completed returns `200` without mutation. Concurrent emulator requests produced one `202`, one `409`, and one deterministic retry audit event. The API does not call Firebase Auth. The existing SW-01.8C bounded processor discovers the due pending record and retains its established one-minute claim lease, heartbeat and fencing checks. It revokes only the UID read from the stored operation. Existing failure policy returned a permanent Auth failure to `manualReview` in the test. The tests verified suspended/disabled user-access records remained unchanged.

## Remaining limitations and completion

- The audit schema cannot record operator reason/reference; this endpoint does not accept arbitrary text to work around that limitation.
- The API requeues work but does not expose manual-review browsing, operation editing or direct database repair. A monitored, approved operator runbook remains necessary before production use.
- Production scheduling, IAM, monitoring and deployment remain separate authorization decisions.

**Completion boundary:** SW-01.8D implementation and local regression verification are complete. No production scheduling or deployment was started.
