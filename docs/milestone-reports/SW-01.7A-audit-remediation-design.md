# SW-01.7A — Privileged Mutation Inventory and Audit Remediation Design

**Review date:** 2026-11-08  
**Status:** Investigation and design complete; implementation not started.  
**Scope:** Privileged mutations, durable audit strategy and fail-closed account suspension. No application code or production resource was changed.

## 1. Executive summary

The existing registry operations for device registration, association and product reassignment commit their Firestore mutation and success audit event in one transaction. The initial Super Admin bootstrap also includes its Firestore audit event in the transaction.

Several other privileged Firestore mutations persist the business change first, then call `recordAuditEvent` separately. If audit persistence fails, the API can fail after its mutation committed, leaving no durable success audit event. Affected operations include account provisioning/suspension, product and firmware-release changes, installer assignment and installation progress/completion. The session sign-out endpoint also revokes Firebase Auth refresh tokens before writing its audit event.

Suspension currently commits Firestore access/profile changes, then marks the Auth user disabled, then writes a separate audit event. Server authorization rejects the Firestore suspended state and disabled Auth account, so the implemented ordering is fail-closed for HomeGrid access once the Firestore batch commits. However, there is no durable cross-system intent/retry record, `revokeRefreshTokens` is not called by suspension, and failures can leave incomplete or unaudited work.

**Recommendation:** use one Firestore transaction for each Firestore business mutation plus its corresponding audit event. For Auth suspension, use a small Firestore outbox/state record and two audit milestones: durable request/deny-access intent, then completion after Auth disable and refresh-token revocation succeed. Keep the account's Firestore access state suspended throughout retries. Do not implement reactivation in the suspension path.

## 2. Inventory scope and evidence

Inspected all write APIs under `src/app/api/`, `src/services/security/protected-operations.ts`, auth/session services, `src/services/audit/server-audit.ts`, Firebase models/rules and `scripts/bootstrap-super-admin.ts`. Tests and emulator fixtures were reviewed to distinguish production operations from test-only writes.

The existing Firestore client rules deny all client reads and writes. The inventory below describes trusted server Admin SDK writes, Auth Admin writes and trusted operator actions. The Super Admin permission matrix remains unchanged.

### Mutations explicitly absent or non-privileged

- There is no production API to create/update households or household memberships, change customer records, edit installer profile records, mutate diagnostics records, delete audit events, change user roles, reactivate accounts, or control appliances. Existing read routes do not mutate these records.
- Public email/password registration changes Firebase Auth only. It does not write `users`, `userAccess`, a role, or an audit event; an unprovisioned identity has no HomeGrid application access. It is not a privileged application mutation.
- Simulator test fixtures and their cleanup are emulator-only test utilities; they are not production API operations. Simulator APIs reuse the audited registry services listed above.
- Audit events are appended through trusted server code. Firestore client rules deny client audit writes; no application API for editing/deleting audit events exists.

## 4. Current consistency classification and common risks

| Classification | Operations | Result |
|---|---|---|
| Atomic Firestore business mutation + success audit | Device register/associate/product-reassign; bootstrap | Firestore commit is all-or-nothing for those writes. Keep as the model. |
| Business mutation atomic internally, but audit separate | Account profile/access provisioning batch; installation progress/completion transaction; installer assignment transaction | Business documents commit together, but can commit without audit. |
| Business write and audit both separate/non-transactional | Product create/state, firmware-release create/state | Mutation can be unaudited; validation reads can race state changes. |
| Cross-system Auth + Firestore + audit | Account suspension; session revocation | No distributed transaction. Requires durable intent, idempotent retry and explicit pending/completed status. |
| Audit-only action, no protected business mutation | Authorization-denied events | Access stays denied on audit failure; failure affects observability/HTTP error, not authorization. |

Additional findings:

- `recordAuditEvent` appends with `.add()` and is not transaction-compatible. A Firestore transaction cannot safely call it because transaction callbacks may retry and external writes inside the callback can duplicate.
- Some atomic registry transaction callbacks create an audit document reference and `correlationId` inside the retryable callback. Only committed Firestore transaction writes survive a retry, so that does not currently commit duplicate events, but reference/ID generation should move outside the callback to keep the logical operation identity stable across retries.
- A Firestore transaction retry is not the same as an HTTP retry. Random document IDs for device registration and firmware release can create duplicate resources if a client retries after a lost response. `assignInstaller` and repeated suspension can also produce duplicate success events today.
- Existing successful events contain actor UID/role, action, resource type/ID, outcome, correlation ID and server timestamp. Keep these fields; add only bounded operation metadata needed for idempotency/recovery. Never record ID tokens, session cookies, private keys or raw credentials.

## 5. Recommended Firestore transaction strategy

### 5.1 Shared transaction-safe audit primitive

Refactor the audit boundary into two deliberately separate uses:

1. A pure builder such as `buildAuditEvent(...)` that derives a validated event record from server-verified actor/context, one stable correlation/operation ID and server timestamps. It performs no Firestore I/O.
2. A transaction-aware writer/helper that accepts an already-created audit document reference and writes via `transaction.create(auditRef, event)`. Continue to keep the public `recordAuditEvent` append helper for audit-only events that have no paired business mutation.

Generate the audit reference, correlation ID and stable operation ID once before entering a transaction callback. Inside the callback: perform all reads and validation first; then write the business document(s) and `transaction.create` the audit event. Never write an audit success event before a business mutation, and never call an external service or standalone audit write from a retryable transaction callback.

Use `transaction.create` rather than overwrite so a duplicate event ID cannot replace prior evidence. If the audit create fails, Firestore aborts the entire transaction. Firestore transaction retries then commit no more than one copy of that event document for one operation ID.

### 5.2 Apply the pattern consistently

Use transactions for state-dependent mutations so current-state validation and the mutation are in one boundary:

- Product create: create the deterministic product doc and event together.
- Product state update: read current state, validate transition, update and create event together.
- Firmware-release create: read/revalidate product state, create release and event together.
- Firmware-release state update: read current state, validate transition, update and create event together.
- Installer assignment: read installer/access and installation, update and create event together.
- Installer progress/completion: read assigned installation/current state, validate and update plus event together.
- Account provisioning: retain the current create-only semantics; add the success audit event to the same batch or transaction as the role/profile documents. Prefer a transaction if idempotency receipt or existing-data reads are included.
- Keep existing device registry transaction boundaries and bootstrap boundary.

For a Firestore business mutation that fails validation or commit, do not emit a success event. An optional failure/denial event can be written after the failed transaction with `outcome: failure/denied`; it must name the failed action and must not imply the business mutation committed. If this secondary failure event cannot persist, the failed business transaction still left no mutation.

### 5.3 Transaction retries and duplicate HTTP requests

Transaction retries must reuse one operation ID, correlation ID and audit document reference prepared outside the callback. The Firestore SDK may invoke the callback more than once, but only the successful commit persists the single audit document.

For requests that create a new resource or can be retried after a lost response, add an idempotency mechanism at the API/service boundary. Recommended design: require a bounded `Idempotency-Key`, scope it to authenticated actor + operation/route, persist a hash of the normalized request and the committed result receipt in the same transaction as mutation/audit, and return the stored result for an identical retry. Reusing a key with a different request returns conflict and performs no mutation. Do not store raw keys or secrets. This requires an approved receipt schema/retention policy and backward-compatible API decision; do not silently invent it during implementation.

Natural create-only identifiers already prevent some duplicates (product code and user UID), but do not cover generated device or firmware-release IDs. Validate no-op/update behavior separately; idempotency must not bypass fresh authorization or resource-scope checks.

## 6. Recommended account suspension state machine

### 6.1 Existing authorization invariant

`requireAuthenticatedUser` accepts only `userAccess.state === "active"`, `users.accountState === "active"`, and an enabled Firebase Auth user. Therefore a committed Firestore suspension state already denies HomeGrid application access even if Firebase Auth calls fail. Preserve this invariant. The suspension operation must never restore `userAccess` or profile state to active while Auth revocation is pending.

### 6.2 Outbox/state design

Use a small server-only `accountSuspensionOperations/{uid}` record (or an equivalent one-open-operation-per-UID outbox). Reuse current `UserAccessDocument.state = "suspended"` and `UserDocument.accountState = "disabled"`; do not add an intermediate access state that the authorization layer might accidentally accept.

| State/phase | Firestore transaction | Firebase Auth action | Access result |
|---|---|---|---|
| `active` → `pendingAuthRevocation` | Verify current records; set access `suspended` and profile `disabled`; create the durable operation intent and `accounts.suspension.requested` audit event. Commit together. | None before this commit. | Application access becomes denied immediately on commit. |
| `pendingAuthRevocation` attempt | Record attempt metadata with bounded/sanitized error fields; do not activate any account state. | Set Auth `disabled: true`, then call `revokeRefreshTokens(uid)`. Keep both calls outside Firestore transaction callbacks. | Remains denied even if either Auth call fails. |
| Auth step failure | Keep operation pending; persist attempt/failure outcome and an `accounts.suspension.auth-revocation-failed` event in a Firestore transaction where possible. | Retry may call disable/revoke again; these operations must be treated idempotently. | Remains denied. Do not report completed. |
| Auth disable + revocation succeeded → `completed` | Transaction reads operation, marks complete and creates the `accounts.suspended` completion event using a stable event ID. | Already complete. | Remains denied. |
| Completion transaction fails after Auth succeeds | Leave the existing durable request pending; do not restore access. | Retry disable/revocation safely, then retry finalization. | Remains denied until completion is recorded; no false success. |

The operation record should contain operation ID, target UID, request actor UID/role, correlation ID, status, attempt count, created/updated/completed timestamps and a sanitized last failure code. It must not contain credentials, tokens or sensitive Auth responses. Keep the pending operation enumerable/retryable to authorized operators. Firestore client rules remain deny-all; no client can create or update this record.

### 6.3 API and recovery behavior

- If the initial Firestore transaction fails, do not call Firebase Auth and report the request as failed; no suspension intent or Firestore state change has committed.
- Once intent commits, an Auth failure must never roll back the suspended Firestore state. Return a clear pending result (recommended HTTP 202) rather than a completed-success response. The API response must not expose raw Auth errors.
- Repeating the suspension request for a pending target resumes the same operation, without duplicating the request audit event. A completed request is idempotent. A request for an already-suspended legacy account with no operation record creates a reconciliation intent and runs the same fail-closed process.
- The minimal retry mechanism can be an authorized repeat of the existing Super Admin suspension endpoint plus a trusted operator reconciliation command. A scheduled worker/queue can be considered later if the operational service requires automatic retry; it is not necessary to preserve fail-closed access. Pending operations need monitoring and an owner.
- Record request and completion as separate events so an intent is never mistaken for successful Auth revocation. Use a stable event ID per operation/phase. For asynchronous completion, decide whether the event actor is the original requester plus an explicit system executor field or a system actor with a separate requester field; do not misattribute a worker action.

### 6.4 Repeated suspension and reactivation

Repeated requests while pending resume the existing operation. Repeated requests after completion return the existing suspended result and must not append duplicate completion events. If Auth state is found enabled despite a completed operation, keep Firestore access suspended and open a new reconciliation attempt/audit event; never infer that Firestore state should be reactivated.

Reactivation is a separate, unimplemented operation and must not be added to suspension code. If later approved, keep Firestore access suspended while Auth enablement and refresh-token/session invalidation are handled; only a final transaction may mark the account active and append a completion audit event. Failure before that transaction leaves the account denied. A separate work package must define which roles can reactivate, identity recovery/reauthentication, customer/installer record state, audit actions and operator approval.

## 7. Authorization implications

- No permission changes are proposed. `users.manage` remains required to request/retry suspension; `products.manage`, `firmwareReleases.manage`, `installations.manage`, Installer workflow permissions and device permissions retain their current role mappings.
- Authorization continues to derive from the verified session and current server-managed `userAccess` state. The browser cannot set the suspension state, role, actor UID or audit payload.
- The suspension outbox and retry path are server-only. Any retry endpoint or operator command must verify actor permission/scope and preserve audit attribution.
- Customers remain household-scoped; Installers remain assigned-installation-scoped; Super Admin remains platform-only with no appliance-control permission. Firestore deny-all rules are unchanged.

## 8. Failure-injection test plan

Add a focused audit/remediation test file (suggested `tests/integration/sw-01-7-audit-remediation.test.ts`) using local Auth/Firestore emulators only. Add a small unit suite for the pure audit event/idempotency builders. Inject failures through a test-only audit/Firestore adapter or controlled transaction failpoint; do not weaken Firestore rules.

| Scenario | Injection | Required assertions |
|---|---|---|
| Business mutation fails | Missing target, stale/invalid transition, or transaction rejection before commit. | Business documents unchanged; no success audit event or receipt exists. Failure/denial event, if used, is correctly labeled and does not imply success. |
| Audit write fails with Firestore mutation | Reject the atomic transaction's audit create/commit. | No business mutation commits; response is failure; no success event exists. |
| Transaction callback retries | Force one retry/conflict before final commit. | Exactly one committed business result and one audit event; correlation/event/operation ID remains stable across callback attempts. |
| Duplicate create request | Repeat identical create using the same idempotency key. | Same resource/result returned and one mutation/audit event. Reuse the key with a different payload returns conflict and does not mutate. |
| Intent persistence failure | Fail initial suspension Firestore transaction. | Firebase Auth disable/revoke calls are not invoked; access/outbox/audit remain unchanged; response is not pending/completed. |
| Firebase Auth disable failure | Fail `updateUser(disabled=true)` after intent commit. | `userAccess` remains suspended; operation remains pending; request event is durable; response is not completed; retry can continue. |
| Firebase Auth revocation failure | Disable succeeds but `revokeRefreshTokens` fails. | HomeGrid access is denied; operation remains pending; no completion event; sanitized failure state is retained. |
| Retry after partial suspension | First attempt disables account but token revocation fails; second succeeds. | Same operation ID/request event reused; disable/revoke safely repeated; one completion event; access remains denied throughout. |
| Completion-audit transaction failure | Auth calls succeed, then fail Firestore finalization/audit transaction. | Access remains suspended, durable request remains pending, no false completion response/event; retry finalizes without duplicate completion event. |
| Repeated suspension | Call completed suspension again. | No duplicate request/completion event or new operation; account remains denied and Auth remains disabled/revoked. |
| Repeated installer/product/firmware transition | Repeat identical committed update or race concurrent transitions. | Defined no-op/conflict behavior; no duplicate success audit and no stale-state overwrite. |
| Sign-out audit failure | Revoke Auth tokens successfully, then fail completion audit. | Cookie is cleared, API does not claim durable completion, operation/audit intent remains retryable if the chosen outbox design is adopted. |
| Reactivation after suspension | Attempt activation through suspension endpoint and stale session; separately test future authorized reactivation design only after approval. | Current API cannot reactivate; suspended/old sessions remain denied. No partially completed future activation restores access. |

All emulator tests must force `demo-homegrid`, local Auth/Firestore endpoints and non-production `NODE_ENV`. No production Firebase access is allowed.

## 10. Migration and compatibility considerations

- Existing `UserAccessDocument` already has `active`/`suspended`; keep using those values so authorization remains fail-closed. A new outbox collection is additive and can be denied by the existing catch-all Firestore client rule.
- Existing suspended accounts may have no operation record and may or may not have been disabled/revoked in Firebase Auth. Do not mark them complete by assumption. A reviewed reconciliation must create a pending operation, verify Auth disable/revocation, and then record completion. Historical missing audit events cannot be fabricated as if observed; preserve available evidence and label reconciliation events accurately.
- Existing active accounts are unchanged. Public registration remains Auth-only and cannot write application role/access documents.
- API clients may currently expect a simple success response for suspension. A 202 pending response and status/result shape require an explicit contract update and UI handling; callers must never interpret pending as completed.
- Idempotency keys/receipts introduce a new API and storage contract. Decide scope, key hashing, receipt retention, replay response and conflict behavior before changing endpoints. Existing callers need a compatibility/deprecation strategy.
- Audit document fields are consumed by admin views. Preserve existing fields and action naming where possible; new request/completion actions must be documented and the UI should distinguish pending from completed.
- The bootstrap event and existing device audit records need no data migration. Existing standalone audit event documents remain readable under the Admin SDK.

## 11. Outstanding design decisions

1. Approve idempotency-key header/receipt behavior, retention and response replay semantics, especially for generated-ID device and firmware-release creation.
2. Decide whether session sign-out uses the same durable outbox pattern or retains a documented best-effort audit limitation. The current Auth revocation is irreversible across Firestore transaction boundaries.
3. Select the trusted retry mechanism and operational owner for pending suspension operations (repeat API call/operator command initially versus scheduled worker later), plus monitoring/escalation expectations.
4. Decide asynchronous audit actor attribution while preserving the initiating administrator and the system executor.
5. Define suspension API pending/completed response semantics and admin UI status handling.
6. Define separate reactivation authorization and recovery policy before any reactivation implementation.
7. Set audit retention, access and reconciliation requirements with the appropriate security/data owners.

These decisions do not block the design recommendation: Firestore-only mutations should atomically commit mutation and success audit, while suspension must first commit a durable fail-closed intent and remain denied until Auth disable/revocation and completion evidence are recorded.
