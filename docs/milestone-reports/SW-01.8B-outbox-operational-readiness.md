# SW-01.8B — Outbox Operational Readiness and Recovery Architecture

**Status:** Architecture recommendation completed; production execution remains deferred  
**Date:** 2026-11-09  
**Verification:** Node.js 24.12.0, npm 11.20.0, local Auth/Firestore emulators, `demo-homegrid`  
**Production resources:** None accessed; nothing deployed

## Executive summary

Keep the account-access and session-sign-out coordinators separate. Share only a future scheduled execution mechanism and operational conventions. The smallest suitable initial production design is one private Cloud Run Job, invoked by Cloud Scheduler, running two bounded domain processors with separate retry rules, leases, metrics and error handling. The job must continue one processor when the other reports an error; neither processor should be allowed to mutate the other outbox.

The implementation has the transactional and idempotency foundations for this design, but is not yet production-ready. At the time of SW-01.8B, both processors scanned collections in document-ID order and processed work sequentially; SW-01.8C replaces that local execution behavior with bounded indexed due-operation queries, retaining production-readiness gates for manual recovery/monitoring ownership, IAM role contents, alert thresholds and environment/project mapping. No production architecture was deployed.

## 1. Existing architecture assessment

### Account suspension/reactivation — `accountAccessOperations`

- One current operation document per UID serializes suspension/reactivation. A Firestore transaction commits the intent, immediately denied Firestore account state and request audit before Auth is called.
- The processor may disable/enable Auth and revoke refresh tokens; it checkpoints progress, uses a five-minute lease/fencing token, and finalizes account state plus completion audit transactionally.
- Automatic retry is bounded to five attempts with exponential backoff from 30 seconds to one hour. Permanent Auth errors and exhausted attempts enter `manualReview`.
- A matching pending request can be resumed through the existing protected API. Manual-review restart already exists on the account suspension/reactivation route using `retryManualReview: true`; the service enforces `users.manage` and stages a deterministic retry audit event.
- Authorization checks Firestore account state and the outbox before allowing protected application access. Reactivation only restores application access through its existing ordered coordinator; an operator must never directly edit account state to clear a failed operation.
- `processPendingAccountAccessOperations()` currently paginates the collection by document ID and processes every `pending` or `processing` document sequentially. Per-operation `process()` checks backoff and lease state, but the scan has no explicit batch/time budget and can include not-yet-due work.

### Session sign-out — `sessionSignOutOperations`

- One operation per signed session cookie is identified by SHA-256 digest. The outbox stores the UID and Auth time, not the raw cookie or other credentials.
- A Firestore transaction commits the durable intent and request audit before Auth revocation. Pending/processing/manual-review intent denies the matching cookie in server authorization.
- Revocation failures and completion-audit failures have sanitized, deterministic per-attempt failure records. Completion status and `auth.session.ended` audit event commit together after successful Auth revocation.
- A one-minute lease/fencing token prevents concurrent claims from committing stale Firestore state. Retry state is bounded to five attempts with capped exponential backoff. Permanent or exhausted failures enter terminal `manualReview`.
- The browser retains only an opaque operation ID after a retryable 503, allowing a same-origin retry after the cookie has been cleared. A trusted demo-only scanner also exists.
- `processPendingSessionSignOutOperations()` paginates the whole collection by document ID and processes due pending/expired-processing documents sequentially. It also lacks a production batch/time budget.

These workflows are deliberately not schema-equivalent. Account access is UID-scoped and may enable Auth only during the existing guarded reactivation sequence. Sign-out is session-operation-scoped and can only revoke tokens for the UID bound in its durable record. Both depend on Firebase Auth plus Firestore, but have distinct state transitions, denial behavior, retry classification and audit actions.

## 2. Recommended shared processing architecture

### Recommendation: shared Cloud Run Job execution, separate domain processors

Use one private Cloud Run Job image and one Cloud Scheduler trigger initially. The job entry point invokes two separate processor functions:

1. `processDueAccountAccessOperations(batchBudget, deadline)`
2. `processDueSessionSignOutOperations(batchBudget, deadline)`

Give each processor its own page/batch limit, time budget, result counters, failure boundary and structured completion record. Run the two bounded processor calls independently (for example with `Promise.allSettled`) so a Firestore/Auth failure in one domain does not suppress the other. Keep each coordinator’s existing per-operation lease, idempotency and retry policy. The orchestration layer must not know how to mutate account or session documents itself.

This is smaller than deploying separate worker services now, while the two domain functions remain independently testable and can later be moved to separate jobs without changing their operation state machines. A single process crash can still interrupt both scans for one invocation, but their durable state and leases make the next scheduled run safe. If workload volume, distinct IAM needs or failure isolation grows, split the processors into separate Cloud Run Jobs while retaining one shared deployment pattern.

### Required processor improvements before scheduling production work

- Query due `pending` operations and expired `processing` leases with bounded pages instead of scanning completed and not-yet-due documents. Add and validate the Firestore composite indexes required by those queries.
- Add a maximum records-per-run and wall-clock deadline. Do not start a new claim after the deadline; let the lease recover any interrupted claim. Set the run budget so it remains safely below the shortest one-minute lease, or explicitly renew the lease under the existing fencing-token transaction pattern.
- Make each domain’s failures observable independently. Recoverable operation failures should be persisted and counted rather than causing the entire job to replay the same batch. A worker-level scan/configuration failure should produce a non-zero job result so Cloud Scheduler/Cloud Run can retry the invocation.
- Configure bounded task retry and graceful shutdown. Duplicate scheduled executions are expected to be possible; leases and deterministic audit IDs remain the correctness controls, not scheduler exclusivity.
- Prevent starvation: each scheduled invocation must reserve a bounded budget for both outboxes, even during a large account backlog.

Cloud Run Jobs can be triggered on a schedule by Cloud Scheduler; the Scheduler identity should have permission to invoke only this job. The job uses a dedicated service identity and Application Default Credentials, with no downloaded service-account key. See [Cloud Run scheduled jobs](https://docs.cloud.google.com/run/docs/execute/jobs-on-schedule?hl=en), [Cloud Run job service identity](https://docs.cloud.google.com/run/docs/configuring/jobs/service-identity), and [Cloud Scheduler authentication](https://docs.cloud.google.com/scheduler/docs/http-target-auth?hl=en).

Pub/Sub is not recommended yet: it would add message lifecycle, duplicate-delivery, dead-letter and outbox-to-queue consistency concerns without a demonstrated volume or latency requirement. A continuously running worker service is also unnecessary for these low-frequency workflows.

## 3. Processing-specific requirements

| Concern | Account access | Session sign-out |
| --- | --- | --- |
| Operation identity | UID document key plus stable `operationId`; one current operation per UID. | SHA-256 cookie digest document key; bound UID remains immutable. |
| Auth calls | Suspension: disable then revoke. Reactivation: enable then revoke, then only the existing final transaction may restore Firestore access. | Repeat `revokeRefreshTokens` only for the UID stored in the existing operation. Never enable Auth or edit account state. |
| Access denial | `userAccess`/`users` are denied from intent until the existing valid completion path. | Matching session denied as soon as durable intent exists; Auth revocation invalidates refresh-token-derived sessions when successful. |
| Retry policy | Existing five attempts, backoff 30 seconds to one hour, permanent errors to manual review; matching endpoint can resume/retry with `users.manage`. | Existing five attempts/backoff and sanitized error allowlist; permanent/exhausted failures become terminal manual review. Client retry uses only the opaque operation ID. |
| Lease | Five-minute claim lease with fencing token. | One-minute claim lease with fencing token. |
| Audit | Request, per-attempt failure, manual retry and completion; Firestore intent/finalization writes are atomic with audit. | Request, per-attempt failure, manual retry (proposed), and completion; intent/finalization writes are atomic with audit. |
| Production processing | Bounded due/expired candidate query; preserve separate suspend/reactivate semantics. | Bounded due/expired candidate query; operation remains bound to stored UID and cannot restore a session. |

## 4. Monitoring and alert design

Use structured logs and low-cardinality metrics by `operationType`, `status`, `failurePhase` and sanitized `failureCode`. Do not use UID, cookie digest, email, raw error text or operation ID as metric labels. Restrict access to detailed operation/audit records to trusted operators. Never log cookies, ID tokens, refresh tokens, service-account material or raw Firebase Auth responses.

Monitor these signals separately for each outbox:

- Counts in `pending`, `processing`, `completed` and `manualReview`.
- Age of the oldest pending operation and time since last progress/completion.
- Expired lease count/age compared with the relevant one-minute or five-minute lease.
- Attempts and sanitized phase/code distribution; account `lastFailurePhase`/`lastFailureCode`, sign-out revocation and finalization failures.
- Processing duration, claim-to-completion time, per-run candidates/claimed/completed/retried counts and per-domain scan errors.
- Backlog size and oldest-item age across successive runs.
- Auth/Firestore divergence for accounts with no active operation: `userAccess.state`, `users.accountState` and Auth `disabled` state must agree with the expected active/suspended state. Do not “repair” by directly changing data; send inconsistencies to the authorized account coordinator/manual-review flow.
- Audit persistence fallback logs (`homegrid.security_audit.persist_failed`, account-access failure persistence failure, and session-signout failure persistence failure). These represent possible loss of durable audit state and need a high-priority alert.

Suggested initial alert policy, to be tuned during staging:

| Condition | Initial response |
| --- | --- |
| Any `manualReview` operation | Immediate operator page; access remains denied according to the domain state machine. |
| Audit persistence failure or persistent outbox scanner error | Immediate operator page and incident record; never report the operation successful. |
| Lease expired beyond one additional scheduler interval plus two minutes | Warning on first observation; page if still expired on the next run. |
| Pending age over 15 minutes | Warning; page after 60 minutes or sooner for a high-impact account operation. Thresholds account for existing exponential backoff. |
| Repeated transient failures | Alert on multiple consecutive failures or a rising failure ratio over several runs, not each individual retry. Permanent Auth failure is immediate/manual review. |
| Backlog growth | Warning if oldest age or pending count rises for three consecutive scheduled runs; page if processing stops or age crosses the high threshold. |
| Auth/Firestore account-state divergence without an active operation | Immediate security/operations alert; do not automatically restore access. |

Use Cloud Logging and Cloud Monitoring alerting with an on-call owner and documented runbook. Keep raw operation identifiers only in access-controlled logs if needed to correlate with Firestore records; metrics remain aggregated.

## 5. Manual recovery architecture

### Account operations

The current protected suspension/reactivation API already supports an explicit manual-review retry. Keep it as the only application-facing account recovery path: authorize `users.manage` server-side, derive the target/operation from server state, require the explicit retry flag, preserve the original operation ID, increment the manual retry counter, and atomically append the deterministic retry-request audit event. Preserve existing coordinator ordering. In particular, a reactivation retry must not clear `userAccess.state=suspended` or `users.accountState=disabled` before Auth enablement and refresh-token revocation have succeeded.

### Session sign-out

SW-01.8A did not include a manual-review retry API. SW-01.8D implemented the approved application recovery endpoint:

`POST /api/admin/session-signouts/{operationId}/retry`

Authorization uses the existing server-side `users.manage` permission and same-origin active operator session. The API accepts only the operation ID path and derives the UID from the existing record. The transaction requires `status=manualReview`, resets the automatic attempt count, increments the existing `manualReviewCount`, sets the same operation to due pending, clears transient failure/lease fields and appends `auth.session.sign_out.retry-requested` at a deterministic retry-round ID. Pending/processing requests conflict; completed remains completed. The API makes no Auth call. Only the existing processor may call `revokeRefreshTokens(storedUid)`; it cannot enable Auth or restore HomeGrid access. The audit schema does not support an operator reason/reference field, so the endpoint accepts no free-text metadata.

For both operation types, keep audit history append-only even where the outbox document is updated in place and record the initiating operator UID/role. Account recovery reason/reference handling follows its existing approved contract. The session audit schema has no reason/reference field, and SW-01.8D does not add free-text metadata. Never provide a generic “edit operation” endpoint or direct Firestore console repair procedure as the normal recovery path.

The API only requeues a manual-review operation. Operational investigation, safe endpoint use, monitoring and escalation still require a separately approved runbook. Do not grant operators broad Owner/Editor or direct client database access to work around this limitation.

## 6. Production deployment recommendation

**Future option:** one Cloud Scheduler job (initially every one to five minutes, based on backlog targets) starts one private Cloud Run Job. Use one task, bounded batch/time budgets, controlled processor concurrency, and task retry limits. Set a single dedicated runtime service account. Scheduler uses a separate invoker service account restricted to this specific Cloud Run Job; it does not receive Firestore/Auth data permissions.

**Identity and Firebase permissions:** use Cloud Run Application Default Credentials and attached workload service identity, never a downloaded JSON service-account key or `GOOGLE_APPLICATION_CREDENTIALS`. Firebase documents project IAM permissions for Authentication and Firestore; define a custom role containing only the Firebase project access prerequisites and exact Auth user get/update and Firestore entity operations the processors use, then verify it in a separate staging project before production. Do not grant project Owner, Editor, Firebase Admin or broad datastore admin roles by convenience. Firestore's common data role is project-scoped in the published role table, so confirm whether database-level IAM/custom-role conditions are available for the selected database before claiming collection isolation. References: [Firebase IAM permissions](https://firebase.google.com/docs/projects/iam/permissions), [Firestore IAM roles](https://docs.cloud.google.com/iam/docs/roles-permissions/firestore), [Cloud Run service identity](https://docs.cloud.google.com/run/docs/securing/service-identity).

**Environment separation:** deploy distinct jobs, service accounts, Scheduler invokers, Firebase project IDs, alert channels and secrets/config for development, staging and production. Production must reject emulator hosts and `demo-*` IDs. Validate the full IAM policy and a failure-injection/staging run before promoting a container digest. No Firebase service-account private keys belong in environment variables, artifacts or source control.

**Shutdown and retry:** Cloud Run can retry a failed job execution, and Scheduler can retry failed invocations. These retries may duplicate a scan; leases, stable operation identifiers and idempotent Auth calls remain authoritative. On SIGTERM, stop claiming new work, finish or abandon in-flight work safely, and rely on lease recovery. Operation-level transient failures should persist backoff state and not trigger whole-job replay. Bound tasks so the shortest lease is not routinely exceeded; validate Firebase Auth request duration and Firestore commit latency in staging.

**Operational ownership:** assign a software on-call owner for job health/backlog, a Firebase/IAM owner for service identity and project IAM, and a security/audit owner for manual-review/audit-failure incidents. Runbooks must cover retry authorization, account-state reconciliation, sign-out completion verification, credential-free logging, escalation and retention policy.

**Cost and complexity:** Cloud Scheduler pricing is per configured job, while Cloud Run Jobs are billed for task resource duration with a minimum one-minute charge; actual costs depend on region, task sizing, execution frequency, retries and existing account free-tier usage. Firestore reads/writes, logs/metrics and alerting add usage. A single shared job avoids duplicating schedules and deployment artifacts; two independent jobs increase isolation and IAM configurability but add scheduler/job/service-account/alert configuration. Price through the selected region’s calculators and billing account before approval; do not infer production cost from emulator tests. References: [Cloud Scheduler pricing](https://cloud.google.com/scheduler/pricing) and [Cloud Run pricing](https://cloud.google.com/run/pricing).

## 7. Security and authorization requirements

- Worker is trusted server code using Firebase Admin SDK only; no browser can read/write either outbox because Firestore client rules remain deny-all.
- Scheduler identity may invoke only the worker job; worker identity may access only required Firebase Auth user operations and Firestore data operations.
- Do not accept an arbitrary UID for outbox recovery. Bind recovery to the stored operation document and its existing immutable identifiers.
- Preserve account and session denial behavior during pending, processing and manual review. Only the existing reactivation success transaction may restore HomeGrid account access.
- Do not let session sign-out retry call Auth enable/update operations; it only repeats refresh-token revocation for the stored UID.
- Audit every manual recovery with stable event identity, actor and outcome. Do not expose operation details to Customer or Installer interfaces.
- Keep three application roles unchanged. Super Admin platform administration remains separate from appliance/household operation; no device-control capability is introduced.

## 10. Outstanding production decisions and blockers

1. Implement bounded due/expired candidate queries and required indexes; the current whole-collection scans are the primary scale/read-cost blocker.
2. Select batch sizes, per-workflow concurrency, job deadline, schedule interval and queue-age SLOs using staging workload tests.
3. Approve and test minimal Firebase Auth/Firestore IAM roles for the dedicated Cloud Run Job identity; confirm the smallest Firestore IAM scope available.
4. Establish production Scheduler/Cloud Run ownership, incident response, monitoring, alert routing and audit/outbox retention.
5. Approve/implement audited session sign-out manual-review retry using an authorized server-only API; account manual retry already exists.
6. Define how initial sign-out intent persistence failure is handled operationally. The existing route correctly avoids revocation without a durable intent; no outbox can recover an intent Firestore never accepted.
7. Validate lease durations against actual external-call and commit latency. Leases fence Firestore commits but cannot cancel an Auth request already in flight.

No material issue requires stopping implementation for architectural review. Production readiness remains **not approved** until the listed blockers are addressed and validated in staging. No production infrastructure was deployed, and SW-01.8C has not started.
